## Краткий итог

**Состояние: рабочее, но не готово к безопасной публикации в недоверенной сети без дополнительной защиты.**

Основная функциональность inventory/групп/узлов реализована непосредственно в `web1x.py` и связана с `public/main.js`. При этом обнаружены несколько важных эксплуатационных и security-проблем, которые следует закрыть до production:

1. **Высокий риск: отсутствует аутентификация/авторизация HTTP API.** Сервер слушает `0.0.0.0:8000`, а операции изменения inventory и запуска Ansible доступны без проверки пользователя.
2. **Высокий риск: frontend вызывает `/delete_hosts`, но backend на `main` этот POST-маршрут не обрабатывает.** Массовое удаление узлов из текущего UI не работает.
3. **Высокий риск: `/save_playbook` позволяет по имени файла перезаписать любой файл непосредственно в каталоге объекта.** `safe()` убирает путь, но не ограничивает набор разрешённых файлов. Теоретически через API можно передать `hosts.yml`, `defaults.yml` или `ansible.cfg`.
4. **Средний риск: `/playbook` читает произвольный файл из каталога объекта по basename.** Для UI это используется как загрузка playbook, но сервер не проверяет, что имя действительно относится к разрешённому playbook.
5. **Средний риск: `save_hosts()` сериализует inventory заново при cleanup.** Это может менять форматирование, комментарии и другие YAML-конструкции пользователя.
6. **Средний риск: inventory и execution log доступны через API без разграничения доступа.** Это может раскрывать IP, переменные и вывод Ansible.
7. **Низкий/средний риск: встроенный HTTPServer не предназначен для TLS/production reverse-proxy режима.** Для внешнего доступа необходим защищённый слой перед приложением.

## Критические/высокие проблемы

### AUDIT-01 — нет аутентификации и авторизации

**Приоритет:** P0/P1  
**Файл:** `web1x.py`

Сервер запускается на `0.0.0.0:8000`. В `Handler.do_GET()` и `Handler.do_POST()` нет проверки пользователя, токена, роли или хотя бы локального источника запроса.

Особенно чувствительные операции:

- `/run`
- `/run_autodeploy`
- `/stop`
- `/add_host`
- `/update_host`
- `/delete_host`
- `/delete_group`
- `/save_playbook`

Также без авторизации доступны `/data`, `/roles`, `/role_file`, `/playbook` и `/log_new`.

**Рекомендация:** перед production добавить authentication/authorization и ограничить bind-адрес либо поставить приложение за reverse proxy с TLS и контролем доступа.

### AUDIT-02 — frontend/backend не совпадают для массового удаления

**Приоритет:** P1  
**Файл:** `public/main.js` ↔ `web1x.py`

`deleteSelectedNodes()` вызывает:

```text
POST /delete_hosts
```

с полем `hostnames`.

В `Handler.do_POST()` на `main` присутствует `/delete_host`, но отсутствует `/delete_hosts`. При нажатии массового удаления frontend получает 404.

При этом backend уже содержит функцию `delete_hosts(project, obj, names)`, поэтому проблема именно в отсутствии HTTP-маршрута.

**Рекомендация:** добавить `/delete_hosts` в `Handler.do_POST()` и проверить ответ/ошибки для частичного удаления. Это следует сделать отдельным кодовым изменением, а не маскировать проблему на frontend.

### AUDIT-03 — `/save_playbook` не ограничен playbook-файлами

**Приоритет:** P1  
**Файл:** `web1x.py`

Текущая логика использует `safe(data.get("name"))` и затем записывает файл в `object_dir`. `safe()` защищает от `../`, но не проверяет назначение файла.

Следовательно, API-запрос с именем вроде `hosts.yml`, `defaults.yml` или `ansible.cfg` потенциально может перезаписать служебный файл объекта.

**Рекомендация:** разрешать только существующие playbook-файлы из `get_playbooks()` либо создавать новые файлы только по явному whitelist расширений/каталога. Служебные inventory/config файлы должны быть недоступны этому endpoint.

## Средние проблемы

### AUDIT-04 — `/playbook` доверяет имени файла

**Приоритет:** P1/P2  
**Файл:** `web1x.py`

`/playbook` использует `safe(name)` и читает файл непосредственно из `object_dir`. Traversal через `../` отсекается basename-нормализацией, но отсутствует проверка, что файл является playbook.

Это позволяет запрашивать содержимое других файлов каталога объекта, если известны их имена.

**Рекомендация:** разрешать только имена, присутствующие в `get_playbooks(project, obj)`.

### AUDIT-05 — повторная сериализация inventory

**Приоритет:** P2  
**Файл:** `web1x.py`, `save_hosts()` / `_cleanup_empty_groups()`

`_cleanup_empty_groups()` загружает YAML через PyYAML и при наличии изменений вызывает `save_hosts()`. Полная сериализация может менять:

- расположение пустых строк;
- комментарии;
- представление некоторых YAML-значений;
- часть исходного форматирования.

Для пустых host mapping используется собственный representer `InventoryDumper`, что исправляет проблему `host: null`, но не делает сериализацию полностью lossless.

**Рекомендация:** для операций удаления/добавления продолжать использовать текстовые операции там, где это возможно; cleanup по YAML-структуре применять только при действительно изменившейся структуре и покрыть тестами комментарии/anchors/нестандартные YAML-конструкции.

### AUDIT-06 — данные inventory и лог выполнения раскрываются без ACL

**Приоритет:** P1  
**Файл:** `web1x.py`

`/data` возвращает параметры узлов, а `/log_new` — журнал выполнения Ansible. В inventory потенциально могут находиться чувствительные переменные.

**Рекомендация:** не отдавать секретные значения в UI без необходимости; ввести авторизацию и, при необходимости, redaction для логов.

### AUDIT-07 — встроенный HTTP сервер не является production perimeter

**Приоритет:** P2  
**Файл:** `web1x.py`

Используется `HTTPServer` без TLS. Для локальной/доверенной сети это может быть приемлемо, но внешний доступ требует reverse proxy/VPN/firewall.

**Рекомендация:** production-схема: localhost/private bind → reverse proxy → TLS → authentication/authorization.

## Проверенные участки без выявленной критической ошибки

### Path traversal

`safe()` используется для project/object/file-name компонентов, а `role_file()` дополнительно проверяет абсолютный путь через `startswith(root + os.sep)`. В просмотре ролей явный traversal через `../` не обнаружен.

### Запуск Ansible

`subprocess.Popen()` получает список аргументов, а не shell-команду; `shell=True` не используется. Это существенно снижает риск shell injection через имена playbook/host.

### ICMP status worker

`host_up()` также использует список аргументов для `ping`. В `status_worker()` общий `ThreadPoolExecutor(max_workers=20)` переиспользуется между циклами проверки.

### HTML escaping

`public/main.js` содержит `esc()` и использует его для hostname, group name, template name, playbook name и других данных перед вставкой в HTML. Это хорошая базовая защита от HTML injection в этих местах.

Остаётся отдельный риск от inline `onclick` и динамического HTML: при дальнейшем добавлении новых полей необходимо не вставлять неэкранированные значения непосредственно в JavaScript-контекст.

## Архитектурные замечания

- Backend и frontend находятся в небольшом монолитном HTTP-сервере; для текущего размера проекта это приемлемо.
- Inventory редактируется как YAML-структура и частично как исходный текст. Такой гибрид требует особенно аккуратных тестов на форматирование.
- Группы поддерживают вложенность через `children`, а cleanup рекурсивно удаляет пустые группы.
- Группы, созданные через модальное окно, фактически сохраняются в inventory при добавлении узла; отдельного backend endpoint создания пустой группы нет. Это следует считать текущей UX-моделью, а не полноценной CRUD-операцией групп.

## Тестирование, которое необходимо добавить

Минимальный regression-набор:

1. Добавление первого/второго/третьего host с пустыми строками между узлами.
2. Удаление первого, среднего и последнего host с сохранением разделителей.
3. Переименование host с и без групп.
4. Добавление/удаление host из нескольких групп.
5. Удаление последнего host из группы и recursive cleanup `all.children`.
6. Массовое удаление `/delete_hosts`.
7. Попытка `/save_playbook` с `hosts.yml`, `defaults.yml`, `ansible.cfg`.
8. Попытка `/playbook` с именем служебного файла.
9. Inventory с комментариями, пустыми строками и nested groups.
10. Path traversal для project/object/role-file/file-name.
